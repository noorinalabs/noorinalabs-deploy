# Runbook: regenerate the org-wide env-inventory

Operational reference for refreshing `docs/env-inventory.{csv,md}` — the
org-wide inventory of every env-var reference across all 7 NoorinALabs repos
(generated by `scripts/env-inventory.py`, scope deploy#116).

**Audience:** SRE engineer running the periodic inventory refresh chore
(deploy#398-style), or anyone whose PR the env-validate `inventory-staleness`
job warns is stale.

## Why this is a periodic chore (and why a naive local regen is wrong)

`scripts/env-inventory.py` scans the **filesystem org tree** — the parent dir
holding all 7 sibling repos — so the inventory's content is a function of the
entire org tree's state. As siblings evolve, the committed inventory drifts and
the env-validate `inventory-staleness` job (deploy#363) emits a `::warning::`
(it stays GREEN — org-wide drift is non-blocking by design; see
`env-validate.yml` and deploy#396). Refreshing it is its own chore.

**Do NOT regenerate against your live local checkouts.** The local org tree
carries other teams' uncommitted edits and wave branches, so a local regen is
**non-deterministic** and will not match what CI sees. You must regenerate
against the **exact clean refs the CI `inventory-staleness` job checks out.**

## The CI ref set (must be matched exactly)

The `inventory-staleness` job in `.github/workflows/env-validate.yml` checks out:

| Repo | Ref the CI job uses |
|------|---------------------|
| `noorinalabs-deploy` | the PR branch (i.e. the current wave branch) |
| `noorinalabs-isnad-graph` | wave branch if it exists, else `main` (`resolve_ref`) |
| `noorinalabs-user-service` | wave branch if it exists, else `main` (`resolve_ref`) |
| `noorinalabs-data-acquisition` | **`main`** (hardcoded) |
| `noorinalabs-isnad-ingest-platform` | **`main`** (hardcoded) |
| `noorinalabs-landing-page` | **`main`** (hardcoded) |
| `noorinalabs-design-system` | **`main`** (hardcoded) |

> Only isnad-graph and user-service resolve wave-aware; the other four are
> pinned to `main` even if a wave branch exists. Regenerating against a wave
> branch for those four would produce an inventory CI considers stale. If the
> workflow's ref policy changes, update this table to match.

## Procedure

Run from a scratch dir — never against the live local org tree.

```bash
SCRATCH=/tmp/env-inv-cleanrefs
rm -rf "$SCRATCH" && mkdir -p "$SCRATCH"

clone() { git clone --quiet --depth 1 --branch "$2" \
  "https://github.com/noorinalabs/$1.git" "$SCRATCH/$1"; }

# Match the CI ref table above. Substitute the in-flight wave branch for
# deploy / isnad-graph / user-service (fall back to main if no wave branch).
WAVE=deployments/phase-4/wave-1
clone noorinalabs-deploy                "$WAVE"
clone noorinalabs-isnad-graph           "$WAVE"   # or main if no wave branch
clone noorinalabs-user-service          "$WAVE"   # or main if no wave branch
clone noorinalabs-data-acquisition      main
clone noorinalabs-isnad-ingest-platform main
clone noorinalabs-landing-page          main
clone noorinalabs-design-system         main

# Generate (env-inventory.py discovers the org tree relative to its own path,
# so this scans the scratch tree and writes the scratch deploy's docs/).
cd "$SCRATCH/noorinalabs-deploy"
python3 scripts/env-inventory.py

# Prove the generated inventory passes the actual CI gate against the clean tree.
python3 scripts/env_validate.py inventory   # -> "inventory: OK ... current", exit 0
```

Then copy the two generated files into your deploy worktree and commit:

```bash
cp "$SCRATCH/noorinalabs-deploy/docs/env-inventory.csv" docs/env-inventory.csv
cp "$SCRATCH/noorinalabs-deploy/docs/env-inventory.md"  docs/env-inventory.md
git add docs/env-inventory.csv docs/env-inventory.md
```

## Verify

- `python3 scripts/env_validate.py inventory` from the scratch clean tree prints
  `inventory: OK (docs/env-inventory.{csv,md} current)` and exits 0.
- The committed counts move (this is expected drift, not a bug). Inspect the
  `**Distinct env vars:**` / `**Total references:**` header lines in
  `docs/env-inventory.md` to sanity-check the delta.

## Out of scope

- The env-validate gate itself (deploy#363).
- Expanding what `env-inventory.py` scans (e.g. the `env/` + `secrets/` tiers).
