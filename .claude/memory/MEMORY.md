- [Command substitution eats your return channel](feedback_command_substitution_eats_your_return_channel.md) — callers allocate as `err="$(scratch_file)"` — a **SUBSHELL**. Anything the library writes to a **variable** dies at that boundary: it ate the cleanup **registry** (so the EXIT drain drained NOTHING and every allocation leaked — the bug the registry was added to fix) and the **error-reason global** (diagnostic printed blank → **inert**, and the PR body claimed it worked). Fix: encode registry in the **filename** (`$$` IS stable across `$( )`; `$BASHPID` is NOT), reason to **stderr** — the only side channel that crosses. **Ask of any shell library: how do callers invoke it? If `$( )`, stdout is your only return channel and variables are a lie.** ALSO: **#629's prescribed fix would have KILLED THE BACKUP** — `trap … RETURN` (a) does NOT fire on a signal (so it never closes the kill it was raised for) and (b) is GLOBAL + stays armed → re-fires on the *caller's* return with `$err` out of scope → `unbound variable` under `set -u`, mid-run. Detonates only when called from another function — which every real caller does. Correct shape: **EXIT-trap drain** (EXIT *does* run on SIGTERM) + a stale-reaper for the untrappable SIGKILL. **An issue's diagnosis and its prescription are separately fallible — implement the brief, then TEST the brief.** deploy#625/#628/#629, PR #661.
- [An anchor is a denylist ONE LEVEL UP](feedback_an_anchor_is_a_denylist_one_level_up.md) — you can invert a guard to an allowlist on the axis you're thinking about and rebuild the denylist in **the contexts you agree to look at**. #637's author argued *"a verb list is a denylist wearing a different hat"* — then anchored `rclone` to a list of shell constructs he'd thought of, and `timeout 300 rclone purge <bucket-root>` in the REAL backup.sh gave **23 passed**. (Also invisible: `sudo`, `eval`, `for … do`, `| rclone rcat`, `xargs -I{}`, `RC=rclone; $RC purge`.) A guard is only as closed as its **most permissive axis** — value / verb / **context** / file-set / **every** remote-bearing arg (not just the first). Fix: anything unparseable is an **OFFENDER**, never a skip. Two traps in the fix: command substitution must RE-ENTER unquoted context (else `out="$(rclone …)"` is skipped and the file goes green by saying NOTHING — calibrate with an unscoped call nested in `"$( )"`, since a must-not-flag fixture can't prove the tracker looks); and keep "≥1 sanctioned arg" ALONGSIDE "every remote arg sanctioned" (an emptied root var is remote-bearing NOWHERE and passes "every" vacuously). **Coda: his own proof harness was broken — a hand-built env killed the module path, pytest never ran, and EVERY mutation reported "RED". A mutation table where everything is red is not a strong result, it is a broken harness.** Only the BASELINE control caught it. deploy#637/#643.
- [Guard the ACTOR, not the STAGE](feedback_guard_the_actor_not_the_stage.md) — restore-verify was **ONE deleted line from overwriting the prod graph on a schedule**: the destructive `neo4j-admin database load --overwrite-destination` is issued by **restore.sh**, which resolves its OWN project and **defaults to the LIVE one** (`${COMPOSE_PROJECT:-${COMPOSE_PROJECT_NAME:-noorinalabs}}`). Delete the caller's one `COMPOSE_PROJECT="$RV_PROJECT"` export → **33 passed, nothing noticed**. `assert_volume_isolation` inspected the throwaway stack — TRUE and IRRELEVANT, because the load ran in a different process addressing a different project: **the guard inspects the stage the actor never stands on, and passes cleanly while the graph is destroyed.** 3 lessons: (1) constrain the process that ISSUES the irreversible call, not your own; (2) **a mutation harness cannot rule out a catastrophe its fakes cannot REPRESENT** (the fake restore.sh ignored COMPOSE_PROJECT, so the disaster had no variable to occur in); (3) `${VAR:-default}` treats EMPTY as unset, and a `set -a` env-load AFTER the default silently blanks it. - [rc is not an authorization signal](feedback_rc_is_not_an_authorization_signal.md) — rclone returns **rc=0 for a listing it is NOT PERMITTED to see** (empty output, not 403) **and rc=0 for a `purge` it could not ENUMERATE** ("success", nothing deleted). So an exit code cannot test an authorization boundary in EITHER direction — and the dangerous one is that a BROKEN boundary over an empty target also reads `0` and ships the hole. Measure CONTENT (against a target proven populated first — `stg/`=9, `prod/`=18) and SURVIVAL under a SECOND, differently-privileged identity; keep both halves (purge OWN prefix must DIE = it fires; purge OTHER must SURVIVE = cannot cross). Aim the destructive probe at an admin-planted DECOY, never real data; mint a throwaway short-TTL key. Generalisation: **an exit code reports whether a tool completed its work, never whether it was ALLOWED to.** deploy#634/#638.
