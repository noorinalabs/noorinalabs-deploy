1. THE WORKFLOW COULD NOT PRUNE.

The caller's canonical_ids extractor was written SINGLE-quoted carrying doubled backslashes:

    sed -n 's/^canonical_ids=\\([0-9][0-9]*\\)$/\\1/p'

Single quotes do no escape processing, so sed received a literal \\( and matched NOTHING,
ever. Measured against the real gate's stdout:

    single-quoted (as shipped): []
    double-quoted (the other one, twelve lines below): [129234]

Two extractors in one file; one was right. On a perfectly valid da#428 artifact the gate
exits 0, the extraction yields empty, and the workflow dies with "provenance gate exited 0
but emitted no canonical_ids". The happy path was IMPOSSIBLE — it would have refused the
first honest artifact anyone published. And the completeness binding, the single gate three
rounds of review produced, the one thing standing between us and da#426's 83.9% deletion,
was UNREACHABLE DEAD CODE.

It failed closed, so nothing was ever at risk. But the error names the provenance gate, so
the gate looks broken, and the fix that suggests itself under pressure is to weaken the
check — the false-FAIL-drives-a-weakened-gate liability I have been arguing against since
round one, authored by me.

And it is the SAME defect as the [0-9a-f] charclass Weronika caught — an extractor that can
never match, whose empty result is a silent zero — reintroduced one layer up, in the caller,
by the commit that fixed it in the gate. My positive control guarded the gate's parser.
Nothing guarded the caller's.

FIX: there is now exactly ONE extractor (record_field), used by both seams. summary_field
delegates to it. A test asserts the count is one: a second extractor is a second chance to
get the shell quoting wrong, and that is precisely what happened.
